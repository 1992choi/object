## 오브젝트 - 기초편
### 절차적인 설계 및 구현
- 절차적인 설계는 로직을 실행 순서대로 클래스 안에 모두 배치한다.
- 데이터가 사용될 문맥을 고려하지 않은 채 설계된다.
- 이로인하여 중앙집중식 제어 스타일이된다.
  - 서비스에서 모든 DAO와 도메인을 호출하는 스타일
  - 만약 데이터를 구현하는 코드가 수정될 때, 다른 코드까지 함께 수정될 가능성이 높다.
  - Ex) 특정 DTO객체에 유효한 날짜 계산을 위한 변수 startDay, endDay가 있다고 가정할 때,   
    getter를 통해 startDay와 endDay를 제공하고 이를 서비스에서 계산을 한다면,   
    변수명이 바뀌거나 판단 기준이 변경되었을 때 서비스 로직까지 수정에 여파가 발생한다.   
    만약 DTO 내부에서 변수를 가지고 유효한지 아닌지의 값만 제공한다면   
    변수명 혹은 판단 기준 변경에 따라 서비스 로직까지 수정되는 일은 없을 것이다.
    - 따라서 데이터를 사용하는 프로세스는 데이터 내부(DTO)로 이동해야한다.
    - 아래 '캡슐화 위반'과 비슷한 맥락.  
- 캡슐화 위반
  - 단순하게 getter와 setter를 제공한다고 캡슐화가 완성되는 것은 아니다.
  - 각각의 데이터가 어떤 문맥에서 사용될지도 모르기 때문에, 데이터가 변경되면 파급효과가 클 수도 있다.
  - 이는 캡슐화를 위반한 것으로도 볼 수 있다.

### 객체지향 설계 원칙
- 설계가 필요한 이유
  - 요구사항이 변경 될 때 코드를 쉽고 안전하게 수정하기 위해.
- 객체지향 설계 원칙
  - 협력에 필요한 행동을 먼저 결정하고 행동에 적합한 객체를 나중에 선택.
  - 객체의 행동을 먼저 구현하고 행동에 필요한 데이터를 나중에 선택.
- 책임을 기반으로 설계 (=책임 주도 설계)
  - 애플리케이션이 제공할 기능 파악
  - 애플리케이션의 기능 요구사항을 시스템의 책임으로 변환
  - 시스템의 책임을 객체의 책임으로 변환
  - 책임을 담당할 적절한 객체 선택
  - 객체의 책임이 외부의 도움이 필요하다면 다른 객체에게 도움을 요청
  - 도움이 필요한 (=책임을 담당할) 적절한 객체를 선택

### 설계
- 설계란?
  - 설계는 굉장히 대단한 것이 아닐 수 있다.
  - 간단한 관점에서 바라보면 코드를 배치하는 방식이다.
- 훌륭한 설계
  - 응집도가 높다.
  - 결합도가 낮다.
  - 캡슐화를 지키도록 코드를 배치한다.
- 응집도
  - 모듈 내부 요소들 사이의 기능적인 집중도
  - 모듈 내부의 데이터와 메서드 간에 관련된 정도
  - 응집도가 '높다/낮다'로 표현
  - 훌륭한 설계는 응집도가 높은 설계
- 결합도
  - 모듈이 외부의 다른 모듈에 의존하는 정도
  - 모듈이 다른 모듈에 대해 알고 있는 지식의 양
  - 결합도가 '높다/낮다' 또는 '강하다/느슨하다'로 표현
  - 훌륭한 설계는 결합도가 낮은 설계
    - 결합도를 낮추기 위해 자주 변하지 않는 안정적인 부분에 의존한다.
    - 안정적인 부분은 추상화된 부분을 뜻하며, 추상클래스나 인터페이스가 될 수 있다.
- 캡슐화
  - 내부의 데이터와 메서드를 하나의 단위로 묶음
  - 외부로부터 데이터에 대한 직접적인 접근 제한
  - 공통 인터페이스를 통한 접근만 허용
  - 변경 관점에서의 캡슐화는 단순 데이터를 감추는 것이 아니라 변경되는 부분을 내부로 숨기는 추상화 기법으로도 볼 수 있다.
    - 데이터 변경으로 인한 파장을 차단할 수 있다.
    - 타입 변경으로 인한 파장을 차단할 수 있다.
- 설계의 핵심
  - 훌륭한 설계란 변경하기 쉽게 코드를 배치하는 것이다. 
  - 모든 설계 원칙과 이론은 변경과 관련되어있다.
    - Ex) SOLID 원칙
  - 디자인 패턴도 변경과 관련되어 있다.
    - Ex) 템플릿 메서드 패턴, 전략 패턴 등
  - 응집도, 결합도, 캡슐화 역시 변경과 관련되어 있다.

## 오브젝트 - 설계 원칙편
### 설계란?
- 설계란?
  - 기능을 구현하는데 적합한 코드의 구조를 결정하는 일
    - 기능
      - 시스템이 외부에 제공하는 행동
    - 구조
      - 기능을 구현하기 위한 코드의 배치
- 객체지향 설계
  - 메시지를 주고받는 객체들의 협력을 기반으로 구조 설계
- 좋은 구조를 설계하는 방법은?
  - 협력적인 객체 구조와 유지보수하기 좋은 코드 구조를 설계할 수 있는 다양한 방법을 익히고 적용
- 대표적인 객체지향 설계 방법
  - 책임 주도 설계
    - 애플리케이션의 기능을 시스템의 책임으로 해석하고, 다시 이 시스템의 책임을 협력을 설계하기 위한 문맥으로 설정
    - 그 후 문맥 안에서 시스템의 책임을 더 작은 객체의 책임으로 할당하면서 기능을 구현
    - 책임 주도 설계에 대한 오해
      - 처음부터 모든 변경을 수용할 수 있는 안정적인 구조로 설계하는 것은 불가능하다.
      - 그렇기 때문에 현재 시점에 가장 단순한 설계를 선택하고, 변경사항이 생기면 변경에 적합한 설게로 개선한다.
      - 겉으로 보이는 동작은 그대로 유지한채 내부 구조를 재구성하는 방식을 `리팩토링`이라고 한다.

### 리팩토링
- `리팩토링`은 어디서부터 시작할까?
  - 메서드 작게 만들기
    - 읽고 이해하기 쉬운 코드가 된다.
    - 버그 수정, 성능 최적화, 메서드 추가가 용이하다.
    - 작은 메서드에는 의도를 표현할 수 있는 이름을 지을 수 있기 때문에, 메서드를 읽는 것만으로도 주석을 읽는 것과 동일한 효과를 낼 수 있다.
    - 메서드가 작으면 명확한 일만 수행하기 때문에 재사용성이 향상된다.
  - 작은 메서드를 만드는 방법
    - 메서드 추출
      - 의도를 드러내는 이름을 짓는게 중요하다.
      - 메서드 추출의 이유
        - 가독성 향상
        - 중복 코드 제거
        - 단일 추상화 수준 원칙을 지켜 추상화 수준 통일

### 단일 추상화 수준 원칙과 조합 메서드
- 단일 추상화 수준 원칙
  - 추상화 수준을 통일할 때 사용되는 원칙이다.
  - 메서드 안의 모든 코드가 동일한 추상화 수준에 있도록 메서드가 추출되어야한다.
- 조합 메서드
  - 동일한 추상화 레벨의 메서드를 조합하면, 메서드를 읽는 것만으로도 문장을 읽는 것과 같은 효과가 나타난다.
    - ```
      public void playGame() {
        enterGame(); // 게임 입장
        greetPlayer(); // 환영 인사
        huntMonsters(); // 사냥 시작
      }
      ```

### 단일 책임 원칙
- 단일 책임 원칙 가이드
  - 책임을 한 문장으로 적어본다.
    - 클래스의 책임을 설명하는데 '그리고', '또는'이 들어가면 여러 개의 책임을 담당하는 클래스의 지표가 된다.
  - 메서드들을 분류한다.
    - 이름이나 목적이 비슷한 메서드들을 그룹으로 묶어 나열해본다.
  - 인스턴스 변수와 메서드 사이의 관계를 살펴본다.
    - 일부 인스턴스 변수가 일부 메서드에 의해서만 사용되는지 살펴본다.
  - 서로 배타적으로 초기화되는 인스턴스 변수가 있는지를 살펴본다.
    - 어떤 변수들이 초기화될 때 함께 초기화되지 않는 인스턴스 변수들이 있는지 살펴본다.
  - 테스트하고 싶은 private 메서드가 있는지 살펴본다.
  - 외부 의존성을 찾는다.
    - 데이터베이스 또는 외부 시스템과의 연동 등과 같이 외부에 위치하는 불안정한 의존성을 찾는다.

### 디미터 법칙과 묻지 말고 시켜라 원칙
- 디미터 법칙 (Law of Demeter, LoD)
  - 디미터 법칙은 객체 지향 설계 원칙 중 하나로, "낯선 친구와는 대화하지 마라"라는 슬로건으로 요약된다.
  - 즉, 객체는 자신이 직접 사용하는 객체와만 상호작용해야 한다는 원칙이다.
  - 캡슐화 위반 문제를 해결할 수 있다.
  - 위반 예시
    - order.getCustomer().getAddress().getZipCode();
    - 이런 식으로 체이닝 호출을 하면, 내부 구조가 바뀌었을 때 많은 부분이 영향을 받게 된다.
  - 준수 예시
    - order.getCustomerZipCode();
    - Order 클래스가 Customer의 정보를 대신 반환하게 하여, 다른 객체의 내부 구조를 외부에 노출하지 않도록 해야한다.
  - 장점
    - 캡슐화 강화 : 객체의 내부 구조가 외부에 노출되지 않음
    - 유지보수 용이 : 내부 구조가 바뀌어도 외부 영향 최소화 
    - 결합도 감소 : 모듈 간 의존성 줄이기
- 묻지 말고 시켜라 원칙 (Tell, Don’t Ask)
  - 객체에게 필요한 정보를 질문해서 처리하지 말고, 그 객체에게 책임을 시켜서 처리하라는 원칙.
  - 잘못된 책임 할당 문제를 해결할 수 있다.
  - 위반 예시
    - if (car.getFuelLevel() < 10) { car.refuel(); }
    - car의 상태를 묻고, 판단도하고, 동작도 내가 결정한다.
    - 즉, 책임이 분산된다.
  - 준수 예시
    - car.checkAndRefuel();
    - car 객체가 스스로 판단해서 필요한 작업을 처리하도록 책임을 위임한 것
    - car 내부 로직이 바뀌더라도 호출하는 쪽은 영향을 받지 않는다.
  - 장점
    - 캡슐화 강화 : 객체 내부 상태를 외부에서 판단하지 않음 
    - 유지보수 용이 : 변경이 객체 내부에 국한됨 
    - 응집도 증가 : 객체가 자신의 책임을 명확히 가짐

### 의존성 역전 원칙
- 의존성 역전 원칙이란?
  - 상위 수준 모듈은 하위 수준 모듈에 의존해서는 안된다는 원칙
- 왜 상위 수준 모듈이 하위 수준 모듈에 의존하면 안 되는가?
  - 변경에 취약해짐
    - 하위 모듈(구현 세부사항)이 바뀌면, 그에 의존하는 상위 모듈(비즈니스 로직)도 영향을 받아 함께 수정해야한다.
    - 이는 코드의 안정성을 떨어뜨린다. 
  - 재사용성이 떨어짐 
    - 상위 모듈이 특정 구현에 종속되어 있으면, 그 모듈을 다른 환경이나 상황에서 재사용하기 어렵다. 
  - 테스트가 어려워짐 
    - 하위 모듈에 직접 의존하면 테스트 시 실제 구현체를 사용해야 하므로, 테스트 환경을 구성하는 데 어려움이 생긴다. 
  - 확장성이 떨어짐 
    - 새로운 구현체를 도입하려면 상위 모듈도 함께 수정해야 하므로, 기능 확장 시 불필요한 코드 변경이 발생한다.
- 이를 해결하기 위해서는?
  - 인터페이스(추상화 계층)를 도입하여, 상위 수준 모듈과 하위 수준 모듈 모두 인터페이스에 의존하게 만들어야 한다.
  - 이렇게 하면 상위 모듈은 구현 세부사항에 영향을 받지 않고, 인터페이스만을 통해 기능을 사용하게 된다. 
  - 그 결과, 구현체 변경이나 테스트, 기능 확장이 용이해지고, 전체 구조의 유연성과 유지보수성이 크게 향상된다.
- 의존성 주입(Dependency Injection, DI)
  - 인터페이스에 의존하도록 설계하더라도, 런타임에는 실제 동작할 구체 클래스가 필요하다. 이 때 사용하는 방식이 의존성 주입이다.
  - 의존성 주입이란, 필요한 런타임 의존성을 외부에서 객체에 주입하는 방법이다.
  - 객체가 직접 구현체를 생성하지 않고, 외부에서 주입받음으로써 결합도를 낮추고 유연성을 높일 수 있다.

### 개방-폐쇄 원칙(Open-Closed Principle, OCP)
- 개방-폐쇄 원칙이란?
  - 소프트웨어 개체(클래스, 모듈, 함수 등)는 확장에 대해 열려 있어야하고, 수정에 대해서는 닫혀 있어야 한다.
  - OCP가 잘 적용되었다면, 이미 제대로 동작하고 있던 원래 코드를 변경하지 않고 새로운 코드를 덧붙임으로써 변경할 수 있게 된다.
  - Ex)
    - A라는 컨트롤러에서 csv 파일을 기반으로 데이터를 읽는 read()라는 메서드가 있다고 가정해보자.
      - List<PhoneNumber> phoneNumbers = csvReader.read();
    - 요구사항이 변경되어 json 또는 xml 기반으로 읽게 된다면, A 컨트롤러도 함께 수정이되야한다.
      - A 컨트롤러가 구체화된 CsvReader에 의존하고 있기 때문
    - 하지만 A컨트롤러가 구체화된 CsvReader에 의존하지 않고, Reader라는 인터페이스에 의존하고 있었다면 A컨트롤러에 대한 수정은 없었을 것이다.
    - 이렇게 변경사항이 발생해도 A컨트롤러에 대한 수정이 없게 된다면, 이는 OCP를 잘 지키고 있는 설계라고 볼 수 있다.
